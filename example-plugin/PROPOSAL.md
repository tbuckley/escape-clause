# Proposal: making the plugin broker real

The current `example-plugin/` broker proves exactly one loop: `request_action(argv)` →
ticket → `./approve REQ-N` touch-file → run on host → channel notification. Everything
else in the parent proposal (§2) is stubbed out. This document proposes the v1 upgrade —
three features, in dependency order:

1. **A web UI** for reviewing and approving/rejecting requests (replaces the touch-file
   verdicts).
2. **Named policy scripts** the agent can discover and trigger, with per-class
   auto-approval and hash pinning.
3. **AI-powered risk summaries** on every ticket, generated by a broker-owned model from
   broker-verified facts.

The pure-plugin shape is unchanged: claude runs interactively, the broker stays a single
stdio process (MCP server + channel). It *grows* an HTTP listener on `127.0.0.1` for the
UI — safe because the broker already runs unsandboxed on the host, and the agent
verifiably cannot reach localhost (parent proposal, Experiments a/5: `curl 127.0.0.1:<port>`
from inside the sandbox fails instantly and leaks nothing).

---

## 0. Groundwork: durable state

Everything below needs tickets that survive a broker restart. Today `pending` is an
in-memory `Map` and the counter resets to 0 every launch (so `REQ-1` is reused —
ambiguous audit trail). Move state into the private store the sandbox already protects
(`~/.clawmini-demo`, covered by `denyRead` + the guard hook):

```
~/.clawmini-demo/
  tickets/REQ-<n>.json   # one file per ticket: argv/policy+args snapshot, reason,
                         #   status, created/resolved timestamps, decision, output,
                         #   reviewer summary (when ready)
  policies/<name>.json   # policy manifest: description, class, sha256, installed-at
  policies/<name>.script # the executable bytes (the ONLY copy that ever runs)
  secrets/password       # web UI login password (seeded on first run, user-editable)
  secrets/sessions.json  # login sessions (HttpOnly cookie tokens), pruned on expiry
  audit.log              # append-only: every request, decision, execution, registration
  counter                # monotonic ticket counter
```

Two properties come for free once tickets are files: the queue survives restarts, and
the ticket **is** the snapshot — argv (or policy+args) is captured at request time and
the approved bytes are what run, closing TOCTOU for argv-style requests. (File-reference
payloads and the CAS from parent-§2 stay out of scope for v1; the request schema below
leaves room for them.)

## 1. The web UI

A single self-contained page served by the broker at `http://127.0.0.1:8790`
(fakechat owns 8787). No framework, no build step — inline HTML + vanilla JS +
server-sent events for live updates, in keeping with the example's size.

**Pages / views**

- **Queue** — pending tickets, newest first, each showing: ticket id, kind
  (raw command / policy run / policy registration), the exact argv or policy+args,
  age, and the reviewer's risk badge once available.
- **Ticket detail** — the approval surface. Renders, in this order:
  1. *Broker-verified facts*: exact argv rendered as a literal array (never joined into
     a shell string), matched policy + class, script diff for registrations.
  2. *Reviewer summary* (§3): advisory panel, streamed in when ready.
  3. *Agent justification*: shown, but visually quarantined — separate box labeled
     "agent's claim (untrusted)". Under prompt injection this field is
     attacker-controlled; the layout must make that legible.
  4. Buttons: **Approve once · Deny · Deny with message**. Deny-with-message feeds the
     text back in the rejection notification — the cheap human→agent channel.
- **History** — resolved tickets from `audit.log`, so "what exactly did I approve?" is
  answerable later.

**Endpoint security** (the demo-grade version of parent-§2's two requirements):

- *The agent can never reach it.* Three independent layers, all already in place or
  free: the sandbox's empty `allowedDomains` blocks bash from localhost (verified);
  the MCP surface has **no resolve tool** — tools can create and read tickets, never
  transition them, so there is no code path from an agent-invokable interface to an
  approval; and the API requires a login session minted from the password in
  `~/.clawmini-demo/secrets/password`, which is denyRead- and guard-protected.
- *Only the user can resolve tickets.* Bind `127.0.0.1` explicitly (never `0.0.0.0`).
  Approvals are `POST` only, carry an HttpOnly `SameSite=Lax` session cookie, and the
  button lives on the page that renders the full payload — there is no approve-by-link
  and no approval without the snapshot displayed. Production hardening (tailnet binding,
  passkey, CSRF beyond SameSite, phone push) stays documented-but-out-of-scope, as in
  the parent proposal.

**The `./approve` / `./deny` scripts are deleted.** The web UI becomes the only human
approval surface, and the 400ms verdict-file poller goes with them — the HTTP endpoint
is the single resolution code path. The audit doesn't need the scripts either: it runs
unsandboxed as the user, so where a test must resolve a ticket (Part F below) it logs in
with the stored password and POSTs to the same endpoint the UI uses.

## 2. Named policy scripts

The policy engine from parent-§2, scoped to what the demo needs. A **policy** is a named
executable + a manifest declaring its class:

- `readonly` → auto-approved: the broker runs it immediately and returns output in the
  tool result (no ticket, no human). Logged to `audit.log` like everything else.
- `private-write` → auto-approved, logged (v1 treats it like readonly; the distinction
  is for the audit trail and future anomaly review).
- `public-write` / `destructive` / any raw argv → ticket + human review, as today.

**Agent-facing tools** (added to the broker's MCP surface):

| Tool | Behavior |
|---|---|
| `list_policies()` | Names, descriptions, classes, arg hints. Free. |
| `check_policy(policy, args)` | Dry run: `auto_approve` / `needs_approval` / `unknown_policy`, plus which class matched. Lets the agent avoid spurious tickets. |
| `request_action({command} \| {policy, args}, reason)` | Extended: raw argv always files a ticket (unchanged); `{policy, args}` consults the class — auto-approve classes execute inline and return output, review classes file a ticket. |
| `register_policy(name, script, class, description)` | **Itself an escalation.** Files a `policy-registration` ticket; the UI renders the full script (and a diff against the existing version, if updating) plus the reviewer's script analysis. On approval the broker writes the bytes to its private store and pins the sha256. |

**Execution semantics** (straight from parent-§2, all cheap to honor):

- The broker runs `execve(storePath, args)` — never a shell, never string-interpolated.
  What a script does with its args is a registration-review concern; the reviewer flags
  `eval`, backticks, and string-built shell inside submitted scripts.
- **Hash pinning is what makes registration review meaningful.** The executable copy
  lives only in `~/.clawmini-demo/policies/` — a path the agent cannot read or write.
  The agent can rewrite its workspace copy of a script all day; the approved bytes run.
  An *update* re-enters review with an old→new diff, which is the alert-fatigue win:
  the human reviews script changes, not script runs.
- Env scrubbed to a minimal set, cwd = the agent workspace, 15s timeout as today,
  output above ~8KB written to a workspace file and returned by path.

**Seed policies** shipped with the example, so the demo shows both classes:

- `host-info` (readonly): a fixed script running `uname -a`, `df -h`, `uptime` —
  demonstrates auto-approve with zero human interaction.
- `fetch-url` (public-write-adjacent — network egress is an exfil channel, so class
  `public-write`): `curl -s --max-time 10 <url>`. Every run needs approval, and the
  ticket surfaces the URL — demonstrating the exfil-safety question from parent-§2 in
  miniature.

## 3. AI risk summaries (the reviewer)

On ticket creation the broker — which runs unsandboxed and has network — makes one
direct Anthropic API call (`claude-haiku-4-5-20251001`; key from `ANTHROPIC_API_KEY`).
Async: the ticket appears in the queue immediately, the summary streams into the detail
page via SSE when ready.

**Input: broker-verified facts only.** Exact argv or policy+args, matched policy class,
the full script (for registrations) or old→new diff (for updates), and the agent's
`reason` — the last explicitly labeled *inside the prompt* as an untrusted claim to be
evaluated, not believed. The plugin broker doesn't see fakechat traffic, so the parent
proposal's provenance log ("which untrusted inputs preceded this request") is not
available here; the summary notes that limitation rather than pretending otherwise.

**Output: strict JSON schema**, e.g.:

```json
{
  "what_it_does": "one-sentence plain-English description",
  "risk": "low | medium | high",
  "flags": ["writes outside workspace", "sends data to <host>", "encoded string in args"],
  "exfil_note": "for network requests: what data could leave, and who could read it there"
}
```

**Rules that keep it honest** (parent-§2, unchanged in spirit):

- The payload it reads may contain injection aimed at *it*: no tools, payloads delimited
  as quoted data, instructed to describe and never follow, response force-parsed against
  the schema (parse failure → "summary unavailable", never a free-text render).
- **Advisory, never load-bearing.** The raw facts render first and always; if the API
  call fails or the key is absent, approval works exactly as before from the facts
  alone. The reviewer annotates; it does not gatekeep.
- Verdicts cached by sha256 of the verified-facts blob — a re-filed identical request
  costs nothing and can't be used to spin the reviewer.

## Audit additions (tests/sandbox-audit.mjs)

New behavioral checks, following the existing Part C/D pattern of proving properties by
ground truth rather than config inspection:

- **Part E — UI unreachable from the sandbox.** From inside a sandboxed session, `curl
  127.0.0.1:8790` and attempt every agent-facing route; assert no ticket state changes
  and no token leaks. Also assert the MCP tool list contains no resolve/approve tool.
- **Part F — hash pinning holds.** Register a policy, approve it (by POSTing to the
  approve endpoint with the token — the audit runs unsandboxed as the user), then modify
  the workspace copy of the script and trigger the policy; assert the *original* bytes
  ran (marker in output). This is the behavioral TOCTOU test.
- **Part G — auto-approve stays in class.** `request_action({policy: "host-info"})`
  executes with no ticket; a raw argv request never auto-executes.

## Build order

1. Durable ticket store + monotonic counter (everything depends on it).
2. HTTP listener + approve/deny endpoints + token; delete the `./approve`/`./deny`
   scripts and the verdict-file poller. *(The loop is testable end-to-end via `curl`
   before any UI exists.)*
3. Web UI page + SSE queue.
4. Policy store, the four tools, execve runner, seed policies.
5. Reviewer call + SSE summary streaming + cache.
6. Audit Parts E–G; update README. The broker just listens on one more localhost port
   (8790) for the UI. Separately, the launch line **drops** `--strict-mcp-config
   --mcp-config .mcp.json`: that flag makes MCP an allowlist but also strips
   *plugin-provided* MCP servers, and fakechat delivers its tools as one — so strict mode
   kills the chat surface. The plugin example falls back to the `permissions.deny`
   denylist for the claude.ai servers (weaker; documented as such). The allowlist posture
   stays in the SDK-driver `../example`, which controls MCP in code without a plugin
   channel.

Estimated size: the broker grows from ~100 lines to roughly 600–800 across
`broker.mjs` (MCP + channel), `server.mjs` (HTTP/UI), `policies.mjs`, `reviewer.mjs`,
`store.mjs` — still one process, still no dependencies beyond the MCP SDK.

## Explicitly out of scope for v1

File-reference payloads + CAS ingestion, cooldowns and rate caps, phone push, passkey +
tailnet binding, the batch audit digest, subagent launching. Each is specified in the
parent proposal (§2, §5) and none is needed to make the three headline features real.
